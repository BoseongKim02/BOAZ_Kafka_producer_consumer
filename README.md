# Kafka 실시간 수강신청 처리 실습

---

- Docker / Docker Compose
- Python 3.11+

- rich

> 모든 실행은 컨테이너 안에서 이뤄지므로 OS(Windows/Mac)와 무관하게 동일한 명령어로 진행됩니다.

### 💡 오늘 실습 내용

- **Part 1.** 실시간 수강신청과 멀티 컨슈머 (Pub-Sub)
- **Part 2.** 장애 복구와 데이터 재생 (Persistence & Replay)
- **Part 3.** 파티션을 이용한 분산 처리 (Scalability)

---

## 🎯 오늘 실습의 목표

수강신청 시즌마다 서버가 터지는 이유, 그리고 그 문제를 Kafka가 어떻게 푸는지를 직접 터미널을 띄워놓고 확인합니다.

**1. 실시간성과 멀티 컨슈머 (Part 1)**

수천 명의 학생이 동시에 누른 신청 버튼이 Kafka를 거쳐 흘러갑니다. 하나의 신청 이벤트가 **'정원 판정'**과 **'신청 로그 기록'**이라는 서로 다른 목적의 서비스에 동시에 전달되는 것을 확인합니다.

→ *Kafka가 실시간 데이터 통로이며, 하나의 이벤트를 여러 컨슈머가 각자의 목적으로 활용할 수 있음을 이해한다.*

**2. 데이터 영속성과 재생 (Part 2)**

정원 판정 서버가 다운되는 동안에도 신청 요청은 계속 쌓입니다. 서버를 복구했을 때 그동안 놓친 신청들을 처음부터 다시 읽어와 정원이 정확히 복구되는 것을 확인합니다.

→ *Kafka가 데이터를 디스크에 보관하며, 오프셋(Offset)을 통해 과거 데이터를 재생할 수 있음을 이해한다.*

**3. 파티션 기반 분산 처리 (Part 3)**

신청이 폭주할 때 컨슈머를 3개로 늘리면, 파티션 단위로 일감이 자동으로 나뉘어 처리됩니다. 동시에 같은 과목의 신청은 항상 같은 파티션으로 들어가 선착순 순서가 보장되는 것도 확인합니다.

→ *수평 확장(Scale-out)과 메시지 키(Key)를 통한 순서 보장을 동시에 이해한다.*

## 📌 이 실습을 관통하는 질문

> "왜 수강신청은 매번 터질까? 그리고 Kafka는 이걸 어떻게 해결할까?"

- 요청이 한꺼번에 몰려도 버퍼 역할을 하는 중간 계층이 있다면?
- 처리 서버가 죽어도 요청이 유실되지 않는다면?
- 처리 속도가 부족할 때 서버만 늘리면 자동으로 분산된다면?

이 세 가지가 오늘 Part 1~3에서 직접 확인할 내용입니다.
